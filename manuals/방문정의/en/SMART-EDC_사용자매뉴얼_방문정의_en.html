Path Project dashboardVisit definition management

Overview

This screen defines the visits that make up the study schedule. The left side is the VisitGroup tree that groups visits, and the right side shows the details of the selected visit. The visits you define here are expanded for each subject to form the visit timeline, so this is build work that must be finished before subject registration.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

+ New VisitGroup — Creates a new unit for grouping visits 1.2.

On the tree, + adds a visit to that group, and pencil edits the group itself. You can drag visits to change their order.

CRF Visit Matrix — Opens the screen where you link which CRF each visit receives 3.1.

Edit — Changes the definition of the selected visit 1.3. Next to it, Deactivate is how you withdraw a published visit. It replaces deletion.

Publish · Create new version — Manages the versions of the definition 2.1.

The Study management > Visit definition item in the left menu is always available as an entry point. You can also get here from the to-do list in design version management.

The navigation path is Dashboard / Visit definition management.

Plan preview — Shows in advance which day each visit you defined will actually fall on 2.2.

Common / All tabs — Filter the list by study arm (Arm). Common visits are shared by all study arms.

This is a published version notice — During the build stage, you can still edit in place after publishing, and you use deactivation instead of deletion.

Key values in the details are Visit code · Visit name · Visit Type · Anchor Type · Offset Days · Repeating · Window Before/After · Allowed subject status 1.3.

Select version — Switches between the versions of that visit. Use View versions next to it to check the differences between versions.

The version number and the publish status badge are shown together in the header of the details.

Precautions

Easily misunderstood behavior

  • • Only the data manager (DM) and workspace administrators can access this screen. Principal investigators (PIs), research nurses and monitors cannot enter it, even to view it. If they need to check the visit plan, ask for the subject visit timeline or the Plan preview results to be shared with them.
Path Visit definition managementAdd new VisitGroup

Overview

Creates a unit that groups visits. Put the major milestones of the study schedule, such as screening stage · treatment stage, into groups, and add individual visits inside them. For a study where the same visits repeat, such as cyclic treatment, turn on Cycle repeat to define the visit once. It is then expanded as many times as there are cycles.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Study Arm * — The study arm of the current tab is selected automatically. Set it to Common and all study arms share it.

Visit Group code * — Use only English letters, numbers, underscores and hyphens. It cannot be changed after creation.

Visit Group name * — The name shown on screen.

Enable cycle repeat — When this is on, you must enter the 1 Cycle period (in days). The maximum number of cycles is optional.

Create — You can select this only after the three required fields are filled in.

Study Arm note — The study arm of the current tab is the default, and you can change it.

Below the code box, the allowed characters and the fact that the code cannot be changed are shown together.

Cycle note — Use this when the same visit repeats in cyclic treatment.

If a required field is empty, a message below tells you what to fill in.

The Arm: Common label at the top of the window shows which study arm tab you are creating the group in.

Precautions

Must check Data corruption · Form cannot be completed

  • • A VisitGroup code cannot be changed after it is created. Deleting a group is possible only in the setup stage (SETUP), so it is already blocked in the test stage. Create the group only after the schedule structure in the protocol is finalized.
Path Visit definition managementEdit definition

Overview

Changes the definition of the selected visit. The Visit code and Visit Type fields are locked with a gray background. You can change the rest freely during the build stage. After you save, the tree and details update right away.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Visit name — The name shown on screen.

Anchor Type — The reference point for counting dates. If you use informed consent/signature as the anchor, that date becomes Day 0.

Offset Days (from anchor) — How many days after the anchor date the visit falls. 0 means the anchor date itself.

Repeating — Whether the same visit repeats.

Window Before/After (days) — How many days before and after the planned date are allowed. The (-N/+N) label on the visit timeline shows this value.

Subject status restriction — The default is No restriction. To allow CRFs to be created only in certain statuses, select from the 10 statuses below.

Save — Applies your changes. Cancel next to it discards them.

Visit code is locked as “cannot be changed after creation.”

Visit Type is locked in the test stage, because it “can be changed only in the project SETUP stage.”

Window After is paired with Window Before.

Status restriction note — “Only subjects in the selected statuses can have new CRFs created for this visit. … Corrections to records already entered are not blocked.”

Precautions

Must check Data corruption · Form cannot be completed

  • • Once the project moves to operation (ACTIVE), editing the definition and creating a new version are both blocked. The only option left is deactivating a published visit, so you must finalize the schedule design during the build stage (setup and test).

Version management

Path Visit definition managementVersion

Overview

To change a published definition, create a new version. The new version is created as DRAFT, and it is applied to subject visits only after you publish it. The Check before publishing revision card above it tells you in advance what publishing will change.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Select version — Switches between that visit's versions. The screenshot shows v2 (DRAFT).

View versions — Check the differences between versions.

Create new version — You can select this only for a published version. If a DRAFT already exists, this option appears faded.

Publish — Publishes the DRAFT. Publishing needs a separate permission, so some people can edit but cannot publish.

Delete — Deletes the DRAFT version. Published versions are deactivated instead of deleted.

Edit — Changes the definition of the DRAFT 1.3.

Check before publishing revision — Gathers the items to check before publishing. ✓ means confirmed, and ℹ means something to be aware of.

“2 CRFs linked (v1: 2)” — Shows how many CRFs are linked to the new version and how that differs from the previous version. If there are 0 links, a button to copy the links appears with it.

The version badge v2 and the status badge DRAFT are shown side by side.

The group, Arm and code stay the same across versions, because they are different editions of the same visit.

Precautions

Must check Data corruption · Form cannot be completed

  • • If you do not publish, no visits are created for subjects. The system expands only published definitions into subject visits, so when only a DRAFT exists, the subject screen simply shows “No visits.” If a definition exists but no published version does, this screen shows a warning, so be sure to check it.
Path Visit definition managementVisitPlan preview

Overview

Calculates in advance which day each defined visit falls on. It draws the preview from the definition values alone, without using actual subject data, so it is meant for checking the schedule design before subjects are registered.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Close — Closes the window. Selecting outside the window does the same.

Description — Shows the registered visit definitions expanded by study arm.

anchor=Day 0 relative days · design-time projection (not tied to actual subjects) — Calculates with the anchor date set to day 0, and cycle groups are expanded cycle by cycle.

Study arm tabs — If there are several study arms, switch between them here to check each one.

Each row is one visit, in this order: D0 (date counted from the anchor date) · code · name · type · anchor · ±0/0 (allowed window).

Precautions

Easily misunderstood behavior

  • • The dates shown here are relative day counts with the anchor date set to day 0. They are not calendar dates. Actual dates are calculated on each subject's visit timeline, because the anchor date, such as the informed consent date, differs for each subject.

Path Visit definition managementCRF mapping

Overview

This screen links which CRF each visit receives. It is a table with visits in rows and CRFs in columns, and a check mark at each intersection means a link. When you first open it, it is in Link view mode, so nothing changes. Click Edit to change links 3.2.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Edit — Switches to a mode where you can change links 3.2.

Form order — Sets the CRF card order for each visit 3.3.

The Link view badge at the top shows the current mode.

Form column sort chip — Shows which visit's card order the columns are currently sorted by. Select × to clear it.

Column headers show the CRF code, name and version. Columns in the DRAFT group are gray and cannot be linked. Publish that CRF first.

Row headers show the visit name, type and code. Use the dropdown below to choose the definition version of that visit.

The check mark at each intersection is a link. Select a linked cell to show that CRF's items on the right.

The legend below lists three states, Required · Optional · Unmapped, along with the sort criteria.

Precautions

Must check Data corruption · Form cannot be completed

  • • A CRF must be published (PUBLISHED) before it can be linked to a visit. A CRF still in progress appears gray in the DRAFT column, and selecting it is blocked. If you cannot link a CRF, first check whether it is published in CRF Management.
Path CRF mappingLink edit

Overview

Click Edit to change links. Each time you select a cell, it cycles in this order: Unmapped → Required → Optional → Unmapped. Changes are saved only after you click Done. To work on several cells at once, use multiple choice.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Done — Saves the changed links. Nothing is saved until you click this button.

Cancel — Discards your changes and returns to view mode.

Select — Turns on multiple choice mode. You can also hold Shift or Ctrl while selecting, without turning on this mode, and the result is the same.

Form order — Same as in view mode 3.3.

The badge at the top changes to Link edit. Check here which mode you are in.

Guide below — “Click a cell: cycles Unmapped → Required → Optional → Unmapped · Save changes with the “Done” button”

Next guide — “Shift/Ctrl+Click or the ‘Select’ button for multiple choice → OPTIONAL in bulk.” It changes several cells at once to Optional (OPTIONAL).

The guide on the right changes to Select a cell in the matrix.

Precautions

Must check Data corruption · Form cannot be completed

  • • Required and Optional mean different things. A CRF linked as Required must be filled in to complete that visit. An Optional CRF can be left blank, and the visit can still be closed. The cycle goes from Unmapped to Required first, so press once more to set an item to Optional.
Path CRF mappingCRF form order

Overview

Sets the order in which CRF cards appear on the subject visit screen. The order you set here is also used to sort the form columns in the matrix. If you match it to the order in which recorders actually enter data, users will not get lost at the site.

Screen guide

Setting Where you operate
Result What the setting above changes
Note

Visit — Select the visit whose order you want to set. The number in parentheses is the number of CRFs linked to that visit.

Drag the handle to change the order.

You can also move items up or down one step at a time with ▲▼.

Close — Closes the window. Clear form column sort next to it only clears the column sort in the matrix and leaves the order itself unchanged.

Description — The order here is both the card order on the subject visit screen and the form column order in the matrix.

The list shows each number with the CRF name and code. The number on the right is the current sort value.

Yellow warning — “N forms with overlapping sort values.” Overlapping positions are shifted by form code, so the display order may change.

Fix for the same warning — Reordering once reassigns the sort values at intervals of 10.

Precautions

Easily misunderstood behavior

  • • Overlapping sort values come from the default values imported from the build file. If you leave them overlapping, the display order may differ from what you intended. When the warning appears, drag the items to reorder them once so the intervals are reassigned.
